## 一、数据口径声明（重要）

页面上的数字分三层。**不标层级的数字一律不上页面。**

### 1.1 可核验（来自 SSOT 与脚本实跑）

| 指标 | 值 | 复算方式 |
|---|---|---|
| 素材条数 | 205 | `wc -l data/养生知识表.csv` |
| 内容主题数 | 8 | SSOT「主题」列去重 |
| 节气覆盖 | 24 / 24 | SSOT「适用节气」列 |
| 体质覆盖 | 9 种 | SSOT「适用体质」列 |
| 工具化率 | 由动作节点状态加权 | `survival_map_data.py` |
| 独占素材条数 | Σ ≡ 205（互斥分摊后逐条可数） | `allocate_materials()` |
| 月产出件数 | 由工序链残余工时推导 | `survival_deep_model.py` |
| 各阶段已落地/待推进任务数 | 对应真实存在的脚本与文件 | 逐条核对 |

### 1.2 口径值（非实测，可被真实记录覆盖）

**各工序单件工时**（`TIME_BASE`，单位：分钟/件）

- 锚点依据：文案类一条成稿的净创作时间显著高于一次校对，校对 ≈ 创作的一个小数量级
- 每个位次都可用真实记录覆盖——**这是最该被真实数据替换的一层**

**有效产出系数 0.55**

一人公司的时间不只花在「做内容」上：

- 多平台分发与排版适配
- 评论区与私信回复
- 数据回看与选题调整
- 素材补充与工具维护
- 状态波动（生病、情绪、低效时段）

单条工序链只占工作时间的约 55%，其余为维持性开销。

> **不扣这一层，算出来的产能会显著高于实际可达水平。**
> 这是修正过的一个真实问题：初版算出「每周 48 件」，失真。

**每周可用工时 24 小时**（6 天工作日 × 每天专注 4 小时）

**瓶颈阈值 25%**（一道工序吃掉四分之一以上精力即为瓶颈）

### 1.3 明确不做的推算

**推演不含收入、转化率与成本预测。**

没有真实定价与转化数据时，任何收入数字都是虚构。校验器会拦截：

- 「预计月入」「保底收入」「预计收入」等表达
- 把工时说成「实测」的表达
- 推演区未声明不含收入预测

## 二、三条结构不变量

### 2.1 `Σ 独占素材 ≡ SSOT 实际条目数`

**为什么需要**：v2 的面积口径是「该位次主素材池在 SSOT 中的条目数」，
但位次的 `themes` 列表互相重叠——食养那 79 条同时被食养内容号主、短视频口播主、
图文笔记、线上课程讲师各算一遍。

结果：十个位次面积之和 **569 条**，而知识表实际只有 **205 条**。
同一批素材被重复计入，treemap 面积完全失真，**"面积越大＝这个位次越大"的读图前提不成立**。

**怎么修**：引入 `THEME_OWNER` 归属表——每个主题只归属一个主位次，
其余引用该主题的位次记进 `pool`（共享取材），不重复占面积。

```python
THEME_OWNER = {
    "食养": "food_channel",   # → 食养内容号主
    "节气": "solar_channel",   # → 节气养生号主
    "体质": "constitution_channel",  # → 体质辨析号主
    "经典": "classic_channel", # → 经典研读博主
    "起居": "routine_channel", # → 起居调养号主
    "自省": "self_reflect",    # → 自省心性号主
    "边界": "monetize",        # → 私域变现主
    "项目": "monetize",        # → 私域变现主
}
```

于是恒等式成立：**Σ 各位次独占素材 ≡ SSOT 实际条目数**。
校验器 `L3 素材互斥分摊守恒` 每次构建都会核对。

### 2.2 面积口径唯一：月产出件数

v2 的面积混用了两种量（素材条数与产出件数），单位不可比。
v3 统一为**月产出件数**——由各工序链的残余工时推导，十个位次同单位、可比、可复算。

素材条数不再是面积，而是独立的「独占素材」指标。

> 复算：`产出件数 = (可用工时 × 有效产出系数) / 单件总工时`
> 校验器核对「10 个位次面积与工序链推导的月产出件数一致」。

### 2.3 必须且仅有一个现金出口

线下诊疗服务停办后，全图一度没有现金出口——一个"生存地图"却没有一条通向钱的路径，说不过去。

结构因此固定为：

| 层级 | 数量 | 位次 |
|---|---|---|
| 素材位次（独占素材，计入面积） | 6 | 食养 / 体质 / 节气 / 经典 / 起居 / 自省 |
| 成品出口（素材来自上游，不独占） | 3 | 短视频图文 / 社群私域 / 线上课程 |
| 现金出口 | 1 | 私域变现主 |

校验器 `L3 现金出口位次在位` 强制断言有且仅有一个现金出口位次。

## 三、九页签详解

### 3.0 变现链路（panel-funnel）

回答"线下交付停办后钱从哪来"。三层结构：

| 层 | 承载位次 | 作用 |
|---|---|---|
| 内容层 | 短视频图文 / 图文笔记 / 课程 | 拉新与信任建立，不直接收费 |
| 沉淀层 | 社群私域主（早报推送） | 把注意力变成可反复触达的关系 |
| 现金出口 | 私域变现主（会员订阅） | 承接沉淀的关系，转为付费订阅 |

每层给出两张卡：承载位次与作用、靠什么能力撑住（含工具化率或合规校验口径）。

**合规纪律**：本页**不出现任何收入数字**。没有真实的定价、转化与续订数据时，
任何收入推算都是虚构。给的是「三环通路判据」：

- 公开内容层：连续 4 周按节奏产出，且每条带出处与免责
- 私域沉淀层：自测工具的使用者中，有明确比例进入早报订阅并留下体质记录
- 现金出口层：订阅者的续订意愿能被记录，而非只统计一次付费

这些是可观测口径，由使用者用自己的真实数据来填。

### 3.1 工序链（panel-chain）

每个位次的完整交付工序，逐步展示：

- 工序序号、名称、状态标签（已进管线 / 半自动 / 纯手工）
- 单件工时（分钟）、占单件总工时百分比（带进度条）
- 前置依赖（来自 `CHAIN_DEPS`，只保留该位次内真实存在的动作）
- 工具证据（指向仓库里真实存在的脚本）
- 瓶颈标记（占比 ≥25% 者标红）

底部给出单位经济五宫格：单件总工时 / 纯手工占用 / 自动化占比 / 月产出件数 / 有效产出系数。

### 3.2 经营推演（panel-sim）

三个参数实时算产能：

| 参数 | 默认 | 含义 |
|---|---|---|
| 每周专注工时 | 24 h | 每周真正投入的专注时间 |
| 瓶颈优化 | 关 | 把瓶颈工序的自动化率提升一档 |
| 自动化投入 | 0 | 追加投入后自动化工序的额外分钟数 |

**推演结果只给件数，不给钱。** 页面在推演区与引擎注释里都写明了这一点。

### 3.3 生成报告（panel-report）

把整张图压成一页可打印的报告：位次清单、素材分布、工具化率、象限归属。

### 3.4 生存模型（panel-model）

横截面读图：象限（规模化 / 提效 / 观察 / 收缩）判定规则与门槛。

### 3.5 案例库（panel-cases）

位次与素材的对应关系，用于反查"这条内容出自哪一批素材"。

### 3.6 90 天路线（panel-roadmap）

四个阶段，每阶段给出：目标、出口条件、未达成则。

### 3.7 风险预警（panel-risk）

六条风险判据，每条绑定**可观测指标 + 判定阈值**：

| 风险 | 判据 |
|---|---|
| 素材见底 | 独占素材消耗速率 > 补充速率 |
| 单点依赖 | 单一素材来源占比 > 60% |
| 口径漂移 | 推算级数据被当实测级引用 |
| 产能虚高 | 实际产出件数 < 推算的 70% |
| 合规风险 | 出现任一红线命中 |
| 现金断链 | 内容产出正常但订阅转化连续为 0 |

### 3.8 免责与口径（panel-notes）

免责在位 + 口径分层说明 + 已知局限。

## 四、工序链的建模方法

### 4.1 动作节点三态

| 状态 | 含义 | 工具化率权重 |
|---|---|---|
| `auto` | 有脚本可直接产出 | 1.0 |
| `semi` | 脚本出初稿，人工改写 | 0.5 |
| `manual` | 纯人工，无工具 | 0.0 |

位次工具化率 = 该位次所有动作节点的状态加权均值。

### 4.2 残余工时推导月产出

```
单件总工时 = Σ(该位次各动作的单件分钟数)
纯手工占用 = Σ(manual 动作的单件分钟数)
可自动化占用 = 单件总工时 − 纯手工占用
单件产出 = 可自动化占用 × 有效产出系数 + 纯手工占用 × 1.0
月产出件数 = 月可用工时 / 单件产出
```

### 4.3 瓶颈判定

一道工序的单件工时占比 **≥25%** 即标红。判定阈值写在 `survival_deep_model.py`，
页面上标注的阈值必须与数据层一致——校验器 `D3 每个风险条目的判定阈值与数据层一致` 会核对。

## 六、已知局限

诚实地列出来：

1. **工时是口径值不是实测值**。真实单件工时需要跑满一个完整生产周期才有意义。
   当前值来自行业锚点推导，用真实记录覆盖后页面会自动重算。
2. **没有真实收入数据**。变现链路只给通路判据，不给金额。
3. **知识表以养生方向为主**，疾病方向的条目在入库时就被去病名、去症状指向，
   所以支撑的是"生活建议"而非"疾病管理"。
4. **校验器是规则匹配不是语义理解**。它能拦住已知的违规模式，
   但拦不住全新的违规话术。所以词表需要持续补充——这是长期活，不是一次性活。
5. **单人执行，没有做过多智能体并发验证**。契约层的并发冲突机制是设计出来的，
   实际只跑过单人场景。
